# Quest VR tracking and dragging — Issue #45

**All four reconciled scenarios pass.** Chromium and Firefox execute the unchanged official Input Selection Sample and Three.js dragging example with the real extension. Primary-source reconciliation replaces the broken Input Tracking application while retaining visible ray/cursor/grip tracking, both-handed dragging, viewer movement, event/frame lifetime, application-controlled exit and meaningful restart. No production API behavior, profiles, capabilities, upstream source bytes or feature requests were changed. The original blocked reports remain historical evidence below.

## Reproduce exactly four scenarios

```sh
npm ci
npm run build:firefox
npm run test:tracking:chromium
WEBXR_FIREFOX_EXECUTABLE="$PWD/test-results/browser-tools/Firefox.app/Contents/MacOS/firefox" \
WEBXR_GECKODRIVER="$PWD/test-results/browser-tools/geckodriver" \
npm run test:tracking:firefox
git diff --check
```

Each browser command selects exactly Input Selection and Three.js dragging on **Meta Quest 3 / immersive-vr / stereo enabled / DOM Overlay Preview disabled**. Both run two sessions per application, including meaningful interactions after restart. There is no general application-suite or independent AI review prerequisite. Obtain official Firefox 157.0/build 20260924084938 and geckodriver 0.37.1 as described in [Firefox setup](firefox-runtime.md#reproduce). Chromium uses the locked Playwright installation's desktop Chromium; `WEBXR_CHROMIUM_EXECUTABLE` can select another executable, whose version/hash the report will record. These are desktop, WebGL-enabled runs, not headset tests.

The runner creates fresh profiles, loads this worktree as an unpacked Chromium extension or temporarily installs generated `build/firefox/`, and opens the inspected tab's genuine extension-registered DevTools panel. It reuses `firefox-driver.ts`, `firefox-upstream.ts`, `firefox-scenes.js` and `cdp-target.ts`. Firefox retains the existing driver/version gates and loopback-only site grants. Chrome uses the existing bundle-entry breakpoint technique to install the scene observer before the remote panel constructs its scene. No `chrome.devtools` object or tab ID is fabricated.

Entry clicks are trusted WebDriver/Playwright clicks on the application's existing button. Exit uses trusted Enter key input on that same application's exit button: the extension's VR mirror overlays the page and intercepts mouse input. Firefox explicitly focuses the owned browser window and the button before WebDriver key actions; Chromium uses `locator.press('Enter')`. No exit listener is replaced and no direct `session.end()` is used to stop application sessions. The separate temporary inline session used only for ownership assertions ends through its public API.

Panel TransformControls objects are located once at their distinct reset poses through the existing Three.js observation hook and retained by object identity for each hand/viewer. Current positions are never used to identify a control during movement. After the first dragging session, both hands are deliberately placed at [0.25, 1.35, -0.8] metres before exit; restarted dragging must move each retained control independently. Every hand pose operation verifies that the other ray matrix stays unchanged. Tests set the real gizmo object's transform and dispatch its normal `change` handler, then wait for the page to consume the corresponding pose. Trigger presses/releases invoke the actual panel buttons. They traverse extension routing and the device adapter normally. Tests never dispatch page XR events or set device gamepad, application selection, object position, renderer controller or session state.

On assertion failure and success, `finally` closes the owned browser context/session and removes its profile; Firefox also uninstalls the temporary add-on and stops geckodriver. Cleanup booleans are recorded and required on completed runs. Downloaded browser binaries and upstream cache remain reusable ignored test tools, not persistent browser installations. No personal browser profile is used.

## Pinned source reconciliation

Original assumption: the unchanged Input Tracking Sample at `fb41c3416496974672e2c766a41c6febcba2d07e` can render finite two-metre cursors and tracked Quest grip models. The [application](https://github.com/immersive-web/webxr-samples/blob/fb41c3416496974672e2c766a41c6febcba2d07e/input-tracking.html) instead passes an XRRigidTransform to a matrix-array [Ray helper](https://github.com/immersive-web/webxr-samples/blob/fb41c3416496974672e2c766a41c6febcba2d07e/js/render/math/ray.js), then reads nonexistent typed-array point properties. Its generic mesh registration also disagrees with the profile-keyed lookup in [InputRenderer](https://github.com/immersive-web/webxr-samples/blob/fb41c3416496974672e2c766a41c6febcba2d07e/js/render/nodes/input-renderer.js). These are application-source mistakes, not missing extension API features. The original browser reports retain both failures.

Correction: substitute the unchanged official [Input Selection Sample at the same pinned revision](https://github.com/immersive-web/webxr-samples/blob/fb41c3416496974672e2c766a41c6febcba2d07e/input-selection.html) for the Sample half of the four scenarios. It retains inline startup, immersive required local-floor and the base-layer path. It calls [Scene.updateInputSources](https://github.com/immersive-web/webxr-samples/blob/fb41c3416496974672e2c766a41c6febcba2d07e/js/render/scenes/scene.js), which correctly constructs rays from matrices and reads typed-array components, and enables profile controller meshes. Cursors must match the actual application hit point or its one-metre fallback along the ray; ray and grip node matrices must match the application's consumed poses, with loaded visible geometry and changed presented output in both eyes.

Rationale: this preserves continuous application-consumed tracking, rendered rays/cursors/grips and unchanged official source/API exposure without introducing nonstandard transforms, empty Quest profiles or test-time source patches. The two-metre placement was a property mistakenly attributed to the original broken application, not a WebXR requirement. Input Selection supports button effects, but the Sample scenario remains a tracking exercise and does not require button interaction. Both-handed dragging/event acceptance stays in unchanged Three.js. All other acceptance, including four scenarios, actual panel input, viewer motion, at least 30 application callbacks, inline resumption, lifetime, restart, provenance and cleanup, remains required. This is the explicitly authorized correction of an AI-authored application assumption, not a waiver for unfinished extension code.

The [Device CRD 2026-06-09](https://www.w3.org/TR/2026/CRD-webxr-20260609/) remains the reference for SameObject source metadata, relative poses, event frames and session ownership. The [Layers WD 2026-08-11 initialization rule](https://www.w3.org/TR/2026/WD-webxrlayers-1-20260811/#initialization) permits projection layers independently of requesting `layers`. No specification rule was altered for an observed failure.
