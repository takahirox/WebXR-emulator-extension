# Quest VR tracking and dragging — Issue #45

**Partial compatibility evidence; Issue #45 is not complete under its original acceptance.** The four required application/browser scenarios execute with the real extension. Both browsers demonstrate tracking rays, correct application-consumed ray/grip transforms, object dragging, event/frame lifetime, application-controlled end and meaningful restart. The unchanged pinned Input Tracking Sample cannot provide its required two-metre cursors or tracked grip models because of two defects in its own source. The focused commands report `blocked-upstream` and exit **1**, preserving these failures instead of certifying full compatibility. No production API behavior, profiles, capabilities or upstream sources were changed.

## Reproduce exactly four scenarios

```sh
npm ci
npm run build:firefox
npm run test:tracking:chromium
WEBXR_FIREFOX_EXECUTABLE="$PWD/test-results/browser-tools/Firefox.app/Contents/MacOS/firefox" \
WEBXR_GECKODRIVER="$PWD/test-results/browser-tools/geckodriver" \
npm run test:tracking:firefox
git diff --check
```

Each browser command selects exactly Input Tracking and Three.js dragging on **Meta Quest 3 / immersive-vr / stereo enabled / DOM Overlay Preview disabled**. Both run two sessions per application, including meaningful interactions after restart. There is no general application-suite or independent AI review prerequisite. Obtain official Firefox 157.0/build 20260924084938 and geckodriver 0.37.1 as described in [Firefox setup](firefox-runtime.md#reproduce). Chromium uses the locked Playwright installation's desktop Chromium; `WEBXR_CHROMIUM_EXECUTABLE` can select another executable, whose version/hash the report will record. These are desktop, WebGL-enabled runs, not headset tests.

The runner creates fresh profiles, loads this worktree as an unpacked Chromium extension or temporarily installs generated `build/firefox/`, and opens the inspected tab's genuine extension-registered DevTools panel. It reuses `firefox-driver.ts`, `firefox-upstream.ts`, `firefox-scenes.js` and `cdp-target.ts`. Firefox retains the existing driver/version gates and loopback-only site grants. Chrome uses the existing bundle-entry breakpoint technique to install the scene observer before the remote panel constructs its scene. No `chrome.devtools` object or tab ID is fabricated.

Entry clicks are trusted WebDriver/Playwright clicks on the application's existing button. Exit uses trusted Enter key input on that same application's exit button: the extension's VR mirror overlays the page and intercepts mouse input. Firefox explicitly focuses the owned browser window and the button before WebDriver key actions; Chromium uses `locator.press('Enter')`. No exit listener is replaced and no direct `session.end()` is used to stop application sessions. The separate temporary inline session used only for ownership assertions ends through its public API.

Panel TransformControls objects are located through the existing Three.js observation hook. Tests set the real gizmo object's transform and dispatch its normal `change` handler, then wait for the page to consume the corresponding pose. Trigger presses/releases invoke the actual panel buttons. They traverse extension routing and the device adapter normally. Tests never dispatch page XR events or set device gamepad, application selection, object position, renderer controller or session state.

On assertion failure and success, `finally` closes the owned browser context/session and removes its profile; Firefox also uninstalls the temporary add-on and stops geckodriver. Cleanup booleans are recorded and required on completed runs. Downloaded browser binaries and upstream cache remain reusable ignored test tools, not persistent browser installations. No personal browser profile is used.

## Pinned source reconciliation and remaining acceptance

| Original assumption in #45 | Primary source and measured correction | Remaining goal |
| --- | --- | --- |
| Input Tracking renders finite two-metre cursors | [Pinned application](https://github.com/immersive-web/webxr-samples/blob/fb41c3416496974672e2c766a41c6febcba2d07e/input-tracking.html) calls `new Ray(targetRayPose.transform)`. Its [Ray helper](https://github.com/immersive-web/webxr-samples/blob/fb41c3416496974672e2c766a41c6febcba2d07e/js/render/math/ray.js) takes a matrix array and returns typed-array `origin`/`direction`. The application additionally reads their nonexistent `.x/.y/.z` properties. Both browsers pass three `NaN` coordinates to the original `addCursor`; JSON represents those values as `null`, and the observer separately records `finite: false`. A conforming XRRigidTransform/typed array cannot make those reads valid. | Finite, visibly tracked two-metre cursors remain **unmet**. A corrected upstream source pin is needed; changing extension transforms into nonstandard array/point hybrids would conceal an application defect. |
| Input Tracking applies grip poses to its models for a Quest source | The application registers default meshes with `setControllerMesh(node, handedness)` and passes `inputSource.profiles[0]` into `addController`. The [pinned InputRenderer](https://github.com/immersive-web/webxr-samples/blob/fb41c3416496974672e2c766a41c6febcba2d07e/js/render/nodes/input-renderer.js) indexes both by `profile + '_' + handedness` and has no generic fallback. Registered keys are `_right`/`_left`; requested keys are `meta-quest-touch-plus_right`/`meta-quest-touch-plus_left`, so `addController` returns before assigning the grip matrix. Both browsers consume the correct grip matrices but fail that lookup. | Visibly moving grip models remain **unmet**. Static generic geometry in screenshots is insufficient proof of a tracked model. A corrected upstream fallback or registration is needed; replacing valid Quest profiles with an empty identifier is not a fix. |

These correct factual assumptions about the pinned application, not the agreed compatibility goal. The original requirements remain recorded here as unmet; this work does not weaken them to turn the suite green. No new controller feature descriptor is needed. The coordinator can use this table to reconcile the Issue/PR against primary evidence. This node was instructed not to comment or open PRs, so no GitHub mutation was performed.

The [Device CRD 2026-06-09](https://www.w3.org/TR/2026/CRD-webxr-20260609/) remains the reference for SameObject source metadata, relative poses, event frames and session ownership. The [Layers WD 2026-08-11 initialization rule](https://www.w3.org/TR/2026/WD-webxrlayers-1-20260811/#initialization) permits projection layers independently of requesting `layers`. No specification rule was altered for an observed failure.

Input Tracking retains its initial inline request and immersive required `local-floor`, selects the **base** layer path and makes no button interactions. The observer records actual application `getPose`, `getViewerPose`, `addLaserPointer`, `addCursor` and `addController` calls. Three.js retains XRButton's optional `local-floor`, `bounded-floor`, `layers`, `depth-sensing`, GPU-only depth usage preference and empty format preference. Actual enabled features are recorded per session; depth sensing is omitted under Quest VR policy. Normal exposure selects **projection** layers. The observer finds the original generated 50-object group and aims at an existing box from 0.65 m along its +Z direction. The unchanged application's own raycaster chooses the actual selected object, which may be a nearer intersecting object. For both hands in both sessions, record its ID, attachment to the real renderer controller, initial/held/released matrices, return to the original group, and unchanged world placement after another controller translation/rotation. Expected held transforms are `newController * inverse(oldController) * originalObject`; release stability tolerance is **1e-5**. No object or selection logic is replaced. Randomly generated object IDs and layouts can differ between executions.

Both eyes must have positive view dimensions and more than 100 colored foreground pixels and 100 distinct colors in the connected presentation canvas. Screenshots show identifiable cave/laser or generated-object content. Controller movement must change more than five presented pixels per eye outside the middle third of the lower half, excluding the Sample's central animated stats panel. Records retain full image hashes, changed pixel counts and screenshots after each Sample movement; they do not infer tracking from callback counts or initialization alone.

XR wrappers call originals with the same receiver and arguments, return their results/original request promises, and propagate exceptions. Three.js observation uses `__THREE_DEVTOOLS__` and preserves scene callbacks. Sample method wrappers import its existing InputRenderer in the application's module realm (BiDi in Firefox), preserving its exact module instance. Test globals retain references only for observation and assertions. No library, request option or rendering state is changed.

The pinned WPT revision is `e1859580b5fcf74940a18d2f783296b4961035e3`. Assertion ideas from [`xrInputSource_sameObject.https.html`](https://github.com/web-platform-tests/wpt/blob/e1859580b5fcf74940a18d2f783296b4961035e3/webxr/xrInputSource_sameObject.https.html) and [`xrFrame_lifetime.https.html`](https://github.com/web-platform-tests/wpt/blob/e1859580b5fcf74940a18d2f783296b4961035e3/webxr/xrFrame_lifetime.https.html) are adapted into `tracking-observation.ts`: native fake-device connection/setup is replaced by the actual extension's application sessions and panel. ## Evidence, failures and scope

[Chromium record](webxr-tracking-chromium-2026-10-24.json), [Firefox record](webxr-tracking-firefox-2026-10-24.json), and [screenshots](validation/issue-45/) preserve the executed observations. Paths beginning `test-results/` in the records are reproduction outputs; the same screenshot basenames are checked into `docs/validation/issue-45/`.

Records include exact commands, browser/build and driver versions, executable hashes, Node/tool versions, tested source and extension bundle hashes, served pinned source/asset hashes, feature negotiation, numerical transforms/pixels, console results and cleanup. External motion-controller/input-profile assets and the Karla font retain the application's original URLs. Browser response metadata records actual fetched URLs/status/MIME/ETag; separate retrieval hashes identify the external bytes available after execution and are explicitly distinguished from hashing the original browser response body. No external dependency was redirected to the extension's npm libraries.

Earlier exploratory failures were test setup/observation failures: Chromium context preload did not reach the remote panel; a Page.reload command is unsupported on that subframe (the final driver uses the existing bundle breakpoint/reload technique); a duplicated helper declaration caused a test evaluation syntax error; pointer exit was intercepted by the VR mirror; Firefox key input needed the owned browser window focused; and a white-only laser pixel threshold failed because the upstream beam uses additive alpha blending onto colored scenery (the final check compares changed pixels outside stats). The unsupported protocol command terminated that early exploratory process before its normal `finally`; no associated browser process remained, and its one owned leftover profile directory was subsequently identified and removed explicitly. Final runs and ordinary assertion failures used normal cleanup. Typecheck failures during authoring were corrected. The initial finite-cursor assertion exposed the real pinned upstream defect, now retained as a blocker. Successful earlier exploratory reports did not yet distinguish that blocker and are superseded by the explicit nonzero final records.

No extension defect requiring a production change was exposed by the completed checks. `npm ci` and `npm run build:firefox` (typecheck, emit, bundles and Firefox package) completed; the two final focused commands executed all four scenarios and exited 1 for the documented upstream blockers; `git diff --check` completed. No required check is recorded as skipped. Full WPT, a generic application-suite rerun, other devices/browser versions and physical hardware were not executed. Historical inventory/reports and every other actionable compatibility dimension remain unchanged. Required post-merge verification: none.

The frame counter includes the one active-frame ownership fixture callback per session. The `before.frames` checkpoint is already at least 30 in every cycle, before any fixture RAF, and counts application callbacks only.
