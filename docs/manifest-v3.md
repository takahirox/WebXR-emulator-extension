# Manifest V3 migration

Issue [#5](https://github.com/takahirox/WebXR-emulator-extension/issues/5) moves the desktop emulator to Manifest V3. The default repository manifest targets Chrome/Chromium; `npm run build:firefox` produces a separate Firefox MV3 package in `build/firefox/`.

## Startup and security

The manifest declares the packaged polyfill and `dist/extension/main-world.js` in the MAIN world at `document_start`, in every matching frame. The initializer calls the existing `WebXRPolyfillInjection()` wrapper and constructs `CustomWebXRPolyfill` synchronously. The generated UMD polyfill artifact, native-WebXR override behavior, and existing WebXR feature scope are preserved. Page scripts can inspect the emulator's `navigator.xr` and XR globals in their first script. This uses [manifest content-script execution worlds](https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts), with minimum Chrome 111 and Firefox 128. It does not create script elements, copy function text, evaluate strings, or load remote code.

`dist/extension/content-script.js` runs in the isolated world. Only this world accesses extension configuration, storage, and the fixed packaged AR-room URL. As before, configuration arrives asynchronously; XR session requests wait for device initialization. The manifest starts the MAIN-world scripts before the isolated script, whose asynchronous configuration fetch cannot precede installation of the polyfill's configuration listener.

The typed CustomEvent bridge remains page-accessible by design: an inspected application can observe or simulate emulator poses. It provides no privileged command execution. Pose messages are validated for finite numeric vectors and permitted controller names, and converted from typed arrays to ordinary arrays before Chrome's JSON message serialization. Invalid page pose payloads are discarded. The room request accepts no URL or path from the page and returns only the packaged asset. Firefox's isolated-to-page bridge still uses `cloneInto`.

HTTP, HTTPS, and file match patterns retain the previous broad access because the emulator must start before applications on arbitrary development sites execute. `activeTab` or permission requests after a toolbar click cannot provide that startup timing. Chrome users must separately enable file URL access. `storage` is the sole API permission; no scripting, debugger, tabs, alarms, remote-code, or unsafe-eval permission is requested. Web-accessible resources retain only the device catalog and room asset, in MV3 object form; scripts are injected by the manifest rather than exposed as web-accessible resources. Browser-internal pages and restricted extension-store pages remain subject to browser restrictions. Matching normal HTTP/HTTPS/file frames are supported; this change adds no promise of early injection into nonmatching `about:blank`, `srcdoc`, `data:`, or sandboxed opaque-origin frames.

## Worker and frame lifecycle

The background TypeScript entry point registers a synchronous `runtime.onMessage` listener. It retains no port arrays, tab registry, or mutable routing state. Panel controls use one-shot `runtime.sendMessage`; the worker broadcasts them through `tabs.sendMessage` to every live content script in the inspected tab. Content messages wake the worker, which sends them to extension pages with Chrome's authoritative sender tab ID. Panels filter by their inspected tab. A sender must belong to this extension; panel commands must originate from the packaged panel document, and content senders cannot supply the routing tab ID.

Each message works after an idle worker restart without reconnecting ports. Closed panels, removed frames, and navigated/closed tabs need no connection cleanup. Callback responses keep only the current delivery operation open; an absent receiver is an ordinary lifecycle event. There are no retry timers or artificial keep-alive loops. Device/stereo configuration remains in extension local storage, and live emulation/UI state stays in the page/panel across worker suspension. A reloaded page loads its stored configuration and sends the existing startup notification so an open panel resends poses. Extension updates/reloads still require reloading inspected pages.

This follows Chrome's [service-worker lifecycle guidance](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle): global state cannot be assumed to survive suspension.

## Firefox package

Firefox does not support `background.service_worker`; it supports MV3 event pages. `build-firefox.ts` copies the packaged scripts, HTML, catalog, icons, and assets, and replaces the background declaration with `background.scripts`. The default Chrome manifest contains no MV2 background keys. The Firefox package also declares a Gecko ID, minimum Firefox 128 for MAIN-world manifest scripts, and no data collection. See Mozilla's [background compatibility documentation](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background) and [content-script documentation](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_scripts).

Load the Firefox package through `about:debugging`, grant site access, and reload inspected pages. Chrome and Firefox use the same stateless router, polyfill, typed event bridge, and panel code. Historical Issue #5 result: Firefox runtime behavior was **unverified** in that environment: the available Playwright Firefox 157 build timed out navigating its internal `about:debugging` page, so temporary-addon installation and DevTools/VR/AR checks could not be performed. Successful packaging and compatibility documentation do not establish a Firefox runtime pass. Older Firefox releases are outside the new package's declared support range.

Issue #37 subsequently establishes a working runtime route on **official Firefox 157.0 build 20260924084938 / geckodriver 0.37.1**. `npm run test:firefox` installs the generated package in a fresh temporary profile, opens the genuine WebXR DevTools panel and exercises six pinned Sample/Three.js profile combinations, real input, presentation and shutdown. See [the reproducible route, observations and evidence](firefox-runtime.md). This does not retrospectively change the failed Playwright installation attempt or verify other Firefox versions.

The active-session extension lifetime watchdog now lives in MAIN. Once per second it synchronously asks the isolated bridge to reply; a removed/invalidated bridge ends presentation. This handles Firefox destroying isolated timers/listeners on unload and does not ping, wake or keep alive the background event page. The timer stops on presentation end/pagehide, and throttled timers cannot be mistaken for a lost heartbeat.

## Validation

These are the original Issue #5 results. The later [Three.js migration](threejs-migration.md) replaces the legacy renderer and records current dependency security and browser checks.

Executed on macOS arm64, Node.js 24.12.0, npm 11.6.2. The browser acceptance run used desktop **Chrome for Testing 155.0.8059.79**, matching the [stable-channel download metadata](https://googlechromelabs.github.io/chrome-for-testing/last-known-good-versions.json) on 2026-10-15. It used a fresh temporary profile, the unpacked MV3 extension, and no MV2 compatibility flags. Playwright software WebGL was enabled; no XR hardware was needed.

- `npm ci`: passed (54 packages installed). npm reports the existing high-severity advisory in retained Three.js; upgrading the renderer is outside this migration.
- `npm run typecheck`: passed for source, build scripts, declarations, and regression tests.
- `npm run build`: passed and generated the new MAIN-world entry point plus existing extension/panel artifacts. The polyfill wrapper and bundle remain unchanged. Rollup still reports the upstream XRSession/XRFrame circular dependency warning.
- `npm run build:firefox`: passed; generated a separate MV3 event-page package. Packaged manifest/HTML paths were checked for existing files.
- `npm run test:browser` with the stable executable override: passed. The harness verifies the MV3 manifest and service-worker target; opens the popup document; runs a first-script check for emulated WebXR and XR globals under a script CSP without inline/eval permission; verifies extension APIs are absent in the page world; opens the actual registered WebXR DevTools panel and loads its assets; stores HTC Vive/stereo-off settings and reloads the panel to restore them.
- The same run starts immersive VR, forcibly stops the actual extension worker through CDP, sends page-to-panel poses, stops it again, and uses panel Reset pose to verify panel-to-page recovery. It drags headset/controller gizmos, observes resulting XR poses, presses/releases select and squeeze, and exits through the panel. All six VR input event types occur once.
- It dynamically creates matching same-origin and cross-origin frames, checks first-script WebXR installation, starts VR in each, stops the worker, broadcasts controls to both, verifies frame-to-panel poses, rejects malformed page poses, removes frames, and verifies later controls still reach the remaining document. Another tab receives no inspected-tab pose commands.
- It selects the AR device, loads/renders the packaged virtual room, obtains two persistent and two transient intersections during touch, verifies select events and camera pose notifications, cancels hit tests, and checks XRRay construction. It ends the session and reloads the page to check synchronous startup and restoration of the stored AR device. Uncaught page errors and XR frame errors are checked. Local screenshots of the panel and AR room were visually inspected.

During development, the new CSP fixture initially blocked the AR loader's local blob textures; the fixture now permits local image blobs while continuing to prohibit inline scripts and eval. Runtime checking also exposed Chrome's typed-array message serialization issue; the bridge normalization fixes it. Worker-stop checks observe CDP running status because current Playwright retains the same Worker object across suspension. Earlier failing runs were corrected before the final acceptance run.

The regression harness retains its existing CDP approach to the real DevTools/OOPIF targets and one-render camera probe for vendor gizmos; no extension APIs, storage, routing, or XR implementation are mocked. Screenshots and downloaded test browsers stay in ignored `test-results/`. The test does not exercise store publication, full WebXR conformance, physical devices, optional real-site examples, browser file-access UI, or other desktop browser versions. Firefox limitations are recorded above. No post-merge verification is required.
